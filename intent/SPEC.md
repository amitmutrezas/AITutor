# Spec: Unstuck, the hint-ladder coding tutor (MVP)

Derived from `intent/INTENT.md`, the approved Product Definition and the Design Handoff. Status: draft, awaiting Amit's approval together with PLAN.md.
Tags: [confirmed] Amit said so. [assumption] my fill-in, change it if wrong. [open] needs a decision (see PLAN.md).

## 1. Scope

### In
1. Five-level hint ladder: Nudge, Concept, Locate, Scaffold, Reveal.
2. Solution firewall: the reference solution is never loaded into the hint model's context at levels 1-3. Enforced in code.
3. Leak check on every hint before display, run outside the model that wrote it. If it trips, show the stored fallback hint for that exercise and level.
4. 6 to 8 AI-generated exercises [assumption], each with tests and a reference solution. An exercise is publishable only if its tests pass against its own reference solution.
5. In-browser editor that runs the learner's code against the tests, with no server-side execution of learner code [assumption].
6. Accounts, Basic and Advanced plans, monthly credits. Hint cost: Nudge 0, Concept 0, Locate 1, Scaffold 2, Reveal 3 [confirmed from article; amounts per plan are open].
7. Razorpay subscription checkout, international cards requested.
8. Saved learner code, viewable and deletable by the learner [confirmed that it is saved; retention is open].
9. Terms, refund and privacy pages, generated by us, reviewed by a person who can judge legal text before going live [confirmed Amit wants them built; review is an assumption].
10. Vercel production deploy. README, LICENSE, CONTRIBUTING.

### Out of first release
Explain-it-back checks, stuck detection, dispute button and review queue, chat-style tutor, BugHunt, adaptive practice, more languages, teen or institutional plans, any plan difference other than credits.

### Language
Amit wrote "use the modern languages for web app development, e.g. nextjs, nodejs, typescript". The app is Next.js + TypeScript on Node. Exercises are assumed to be JavaScript [open: JS, TS or both]. JavaScript runs natively in the browser, which is why it is the default.

## 3. Functional requirements

IDs are stable. Tests and PR descriptions cite them.

### Hints
- **H1** A hint request names an exercise, a level (1-5) and the learner's current code. Levels must be requested; the app never auto-escalates.
- **H2** At levels 1-3 the server builds the model prompt from the exercise statement, tests, learner code and level instructions only. The reference solution field is not selected from the database for these requests. A unit test asserts the prompt builder cannot receive it.
- **H3** At levels 4-5 the reference solution is included in context.
- **H4** Every generated hint passes the leak check before it is returned. Minimum check: normalized token-sequence similarity against the reference solution above a threshold, plus a check that no contiguous run of N solution lines appears. Threshold and N live in config and are covered by evals.
- **H5** If the leak check trips, the model errors, or it times out, the stored fallback hint for that exercise and level is returned and the event is logged. The learner is told it is a prepared hint [open: exact wording, Design question 6].
- **H6** Reveal (level 5) is allowed to show the solution; the leak check is skipped for level 5 only. Level 4 (Scaffold) must not contain the full solution, so the check runs.
- **H7** Hints are cached per (exercise, level, code hash) for a short time to avoid paying twice for a double click.

### Credits
- **C1** Each plan has a monthly credit allowance. Amounts: [open].
- **C2** Cost per level: 0, 0, 1, 2, 3. A request that would take the balance below zero is refused before any model call.
- **C3** Deduction and hint logging happen in one database transaction. A failed hint (model error) is not charged.
- **C4** Balance resets on each successful subscription renewal. Unused credits do not roll over [assumption].
- **C5** Free users [open: is there a free tier?]. Assumed: a free account can use levels 1-2 only.

### Exercises
- **E1** An exercise record has: statement, starter code, tests, reference solution, fallback hint per level, status (draft, verified, live).
- **E2** `pnpm exercises:verify` runs each exercise's tests against its reference solution in a sandbox and sets status. Only `verified` exercises can be set `live`. CI fails if a live exercise does not verify.
- **E3** Exercise generation is an offline script run by a person, never by a learner request. Generated output is reviewed before going live.
- **E4** The tests and starter code must fail against the starter code (otherwise the exercise is already solved).

### Code running
- **R1** Learner code runs in a sandboxed Web Worker (or sandboxed iframe) with a time limit. No network, no DOM access to the host page [assumption].
- **R2** The page shows pass or fail per test, with the failing assertion message.
- **R3** Learner code is never executed on our servers.

### Accounts, saved code, payments
- **A1** Email sign-in via the chosen auth provider [open].
- **A2** The learner's latest code per exercise is saved on run. The account page lists it and offers delete per exercise and delete-all.
- **A3** Retention: saved code is kept while the account exists and deleted with the account [open: Amit to confirm].
- **P1** Plans created in Razorpay as subscriptions. Checkout opens Razorpay; the app trusts only the server-verified webhook, not the client redirect.
- **P2** Webhook handler verifies the signature, is idempotent by event id, and updates plan and credits.
- **P3** Failed or cancelled payment returns the learner to Plans with a clear message and no plan change.
- **P4** Refund and cancellation behavior matches the refund policy page.

### Policy pages
- **L1** Terms, refund and privacy pages exist at `/terms`, `/refund`, `/privacy`, linked from footer and checkout.
- **L2** Privacy page states exactly what is stored (account email, saved code, hint requests, payment status via Razorpay) and what is sent to the LLM provider.
- **L3** Pages carry a visible "last updated" date. A PR touching them needs Amit's explicit approval (POLICY.md).

## 4. Non-functional requirements

- **N1** Security: no secrets in the repo, server-only env vars for LLM and Razorpay keys, input validation with Zod on every route, rate limit on the hint endpoint.
- **N2** Cost: hint model choice is configurable by env var. Log tokens per request so AI cost per learner can be computed.
- **N3** Privacy: do not log learner code in application logs. Hint log stores a code hash, not the code.
- **N4** Accessibility: keyboard reachable editor controls and hint buttons, visible focus, color contrast AA.
- **N5** Performance: hint p95 under 8 seconds including leak check [assumption].
- **N6** Analytics: events from the Design package (screen views, hint requested by level, fallback shown, exercise solved, upgrade clicked, checkout started and completed). No third-party tracker without approval.

## 5. Acceptance criteria (proof)

1. For every live exercise, the reference solution passes all tests and the starter code fails at least one (E2, E4).
2. Prompt-builder test: calling it for levels 1-3 with an object that has a `referenceSolution` field throws or ignores it, and the built prompt contains none of the solution tokens (H2).
3. Leak eval: a fixed set of known-leaky hints per exercise is rejected by the leak check, a fixed set of good hints is accepted (H4). Recall on leaky set at least 95% in CI.
4. Credit tests: refused when insufficient, not charged on model failure, atomic deduction (C2, C3).
5. Webhook tests: bad signature rejected, replayed event ignored, valid event updates plan (P2).
6. Playwright smoke: sign up, open exercise, run failing tests, request Nudge, solve, see complete screen.
7. Pre-launch audit: Amit or a reviewer reads 3 hints per level for every live exercise; leaks under 1% (success metric).
8. Lighthouse accessibility score at least 90 on workspace and plans pages.

## 6. Areas of concern (contradictions and risks)

- Data minimization vs saved code: the article argues for storing little; Amit wants code saved. Resolved by storing latest code per exercise only, with delete controls and a plain privacy page.
- Monthly credits vs the article's daily credits: monthly is Amit's call and is untested. Metric to watch: share of learners who exhaust credits in the first 48 hours. If high, revisit.
- Two-day target vs Razorpay activation and KYC: not in our control. Build checkout in test mode, ship the rest, switch to live keys when activated.
- Generated exercises can be wrong. The self-test reduces this and does not remove it. A human reads each exercise before it goes live.
- Legal text generated by an AI is not legal advice. Pages need review by someone qualified before live payments.
- No user evidence. The plan includes a cheap demand test and learner conversations in Next.
